While prototyping a new clinical research platform, I chose to evaluate Inngest as a durable execution environment. What drove it was record synchronization across tenants. A clinical institution manages its own sites and staff in its tenant. A study sponsor runs studies at some of those sites, and the sponsor's tenant has to reflect what happens there: staff rotations, site updates and patient records. At the institution, those patients are people receiving routine care. In the sponsor's tenant, the same patients are anonymized records. A change on either side had to reach the other, and no request handler could make it happen directly, because every handler ran inside a strict tenant boundary and couldn't touch another tenant's database.

So each cross-tenant change became an event. The tenant that made the change published a fact such as `site.updated` or `patient.updated`, and a durable workflow applied it on the other side, inside that tenant's boundary. Inngest delivered on that. Each workflow step retried on its own, a failed run resumed where it stopped, and producers didn't need to know who subscribed.

I quickly realized there was a critical gap, and it sat right at the start of every workflow. The service saved its rows, committed, and then called `inngest.send()`. That call is an HTTP request. When the Inngest server was unreachable, the send failed after the commit had already landed. The SDK keeps no local buffer to replay from, so the event was gone. Our call sites logged the error and carried on, and a staff rotation recorded at the institution never reached the sponsor's study, with nothing to flag the drift.

We patched it with a nightly reconcile sweep that rebuilt each consumer's data from the authoritative rows. That covered crashed consumers and the initial backfill too, but as a fix for lost events it was a stopgap: up to a day of latency, and one event carried data the producer intentionally doesn't keep, so there was nothing to rebuild it from. The real fix is an old pattern, the transactional outbox, and durable workflow platforms make it easy to forget.

## Durable execution starts one hop too late

Durable execution engines checkpoint a run's progress, so a crash or a failed step resumes where it left off. That guarantee begins when the engine accepts the event or the start request. Everything before that, including the moment your service decides a workflow should run, is still your code, and it lives in a different system from the engine.

Inside a run, the platforms handle this for you. Inngest's `step.sendEvent()` is recorded as a step, so a replayed run doesn't send twice. The unprotected hop is the first one, from your request handler into the engine.

## The dual-write problem, with an order

Tenant sync takes a while to set up, so here is the same failure in a shop. Placing an order inserts a row and should start a workflow that charges the card, reserves stock and emails a receipt. Two systems have to change: your database and the workflow engine. There's no transaction that spans both, so you pick an order and live with its failure mode.

**Commit, then send.** If the send fails, the order exists but nothing ever processes it. The customer saw a confirmation, and no card is charged and no receipt arrives.

**Send, then commit.** If the commit fails after the send, a workflow is now charging a card for an order that rolled back. That's worse.

Retrying the send in the handler narrows the window but doesn't close it. The process can still crash between the commit and the send, and a deploy restarts every process eventually.

## The transactional outbox

The fix is to write to one system in the request instead of two. In the same transaction as the order, insert a row describing the event into an `outbox` table. Either both rows commit or neither does. A separate relay then reads unsent rows, delivers them to the engine, and marks them sent.

<Diagram
  src='/images/posts/durable-workflows-need-an-outbox/outbox'
  alt='The API handler inserts the order and the event into the orders and outbox tables in one database transaction. A relay selects unsent rows with FOR UPDATE SKIP LOCKED and sends each with its outbox id, retrying until accepted. The workflow engine then charges the card, reserves stock and sends the receipt.'
  caption='The request writes to one system. The relay owns the hop to the engine.'
/>

The table is small:

```sql
CREATE TABLE outbox (
  id         uuid PRIMARY KEY,
  name       text NOT NULL,
  payload    jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  sent_at    timestamptz
);

-- Keeps the relay's query cheap no matter how many sent rows remain.
CREATE INDEX outbox_unsent ON outbox (created_at) WHERE sent_at IS NULL;
```

Writing the event is one extra insert inside the transaction you already have:

```ts
await sql.begin(async (tx) => {
  const [order] = await tx`INSERT INTO orders ${tx(input)} RETURNING id, total`;

  await tx`
    INSERT INTO outbox (id, name, payload)
    VALUES (${randomUUID()}, 'shop/order.placed', ${tx.json({ orderId: order.id, total: order.total })})`;
});
```

The relay claims a batch, sends it, and marks it sent. `FOR UPDATE SKIP LOCKED` lets several relay instances run without picking up the same rows:

```ts
async function drainOutbox() {
  await sql.begin(async (tx) => {
    const rows = await tx`
      SELECT id, name, payload FROM outbox
      WHERE sent_at IS NULL
      ORDER BY created_at
      LIMIT 100
      FOR UPDATE SKIP LOCKED`;
    if (rows.length === 0) return;

    // The outbox id doubles as the event id, so a resend is recognised as a duplicate.
    await inngest.send(rows.map((row) => ({ id: row.id, name: row.name, data: row.payload })));

    await tx`UPDATE outbox SET sent_at = now() WHERE id IN ${tx(rows.map((row) => row.id))}`;
  });
}
```

If the send throws, the transaction rolls back and the rows are picked up on the next tick. Keep batches small, since the claim transaction stays open while the request is in flight.

## What you sign up for

**At-least-once delivery.** If the relay crashes after the engine accepts the batch but before the `UPDATE` commits, those rows go out again. In exchange for never losing an event, you will sometimes send one twice. Use the outbox row id as the idempotency key on the way in. Inngest ignores an event whose `id` it has seen in the last 24 hours. Make sure your relay gives up, or alerts, well inside whatever deduplication window the engine offers.

**Idempotent consumers.** The engine's deduplication covers the start of a run, not your side effects. Steps still retry, so a charge or an email should carry its own idempotency key to the provider, and database writes should be upserts or guarded by unique constraints.

**Fat events.** Put everything a consumer needs in the payload, and validate it with a schema when it's read. A consumer that reads the producer's tables to fill in gaps couples the two services again.

**Latency and housekeeping.** Polling adds up to one interval of delay. `LISTEN/NOTIFY` can wake the relay early, and change data capture with something like Debezium removes polling altogether if you already run it. Delete sent rows on a schedule, and alert on the age of the oldest unsent row. That single number tells you when delivery is stuck.

**Keep the sweep.** A reconcile job that re-derives downstream state from the source of truth still earns its place. It covers consumer bugs and backfills. It stops being the only thing standing between you and data loss.

If the workflow can own the write, you can skip the outbox. Start the workflow first with a deterministic id derived from the request, and perform the insert as its first step. There's no dual write because there's only one system of record for that operation. The trade is that your request path now depends on the engine being up, and returning the new row to the caller gets harder.

## Which platforms need one

Every platform below makes runs durable once they start, and every one offers a way to deduplicate the start. None of them can join your database transaction, because their state lives in their own store. So each needs an outbox, or the workflow-first approach, wherever a database write and a start have to agree.

| Platform | How a run starts | Deduplication on the way in | Outbox at the edge |
| --- | --- | --- | --- |
| **Inngest** | `inngest.send()`, an HTTP call to the Inngest server, cloud or self-hosted | Event `id`, deduplicated for 24 hours | Needed. `step.sendEvent()` inside a function is already durable. |
| **Temporal** | Starting a workflow is an RPC to the Temporal cluster | Workflow ID: only one open run per ID, with a reuse policy for later runs | Needed, unless the workflow owns the write |
| **Trigger.dev** | `tasks.trigger()`, an API call to the platform | `idempotencyKey`, with a scope and a TTL | Needed |
| **Vercel Workflow** | `start()`, which enqueues the run on Vercel's infrastructure | Recent SDK versions add an atomic start keyed by your own token | Needed |

Some systems don't need one, because they keep their state in your database:

- **DBOS** stores workflow state in your Postgres. Enqueueing a workflow can happen inside the same transaction as your domain writes, so the dual write never exists.
- **Postgres-backed queues** such as pg-boss and Graphile Worker insert a job row. Do that inside your transaction and the queue table is the outbox. pg-boss accepts your transaction's executor, and Graphile Worker exposes `add_job()` as a SQL function.

That only works when the queue's tables share a database with your data. Self-hosting Inngest or Temporal on the same Postgres server doesn't count, because their writes still happen in their own transactions.

If you run Inngest, Temporal, Trigger.dev or Vercel Workflow, find every place a request commits and then sends an event or starts a run. Each one needs an outbox, a workflow that owns the write, or a sweep that can rebuild what the lost event would have done.
